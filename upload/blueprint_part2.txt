# SECTION 20: ANIMATION BLUEPRINT

## 20.1 Animation Philosophy

Animations serve communication, not entertainment. Every animation on this platform should reduce cognitive load, not add to it. Animations are used to:
- Orient the user (where did this element come from? where is it going?)
- Confirm interactions (the button responded)
- Signal loading states (something is happening)
- Aid transitions (we're moving to a new context)

If an animation doesn't serve one of these four purposes, it is not needed.

## 20.2 Animation Timing

| Type | Duration | Easing |
|---|---|---|
| Micro-interactions (hover, press) | 150–200ms | `ease-out` |
| Element entrance (fade/slide in) | 250–350ms | `ease-out` |
| Page transitions | 300–400ms | `ease-in-out` |
| Drawers & modals | 300ms | `cubic-bezier(0.4, 0, 0.2, 1)` |
| Skeleton shimmer | 1500ms | Looping linear |
| Breaking ticker scroll | 20–40s (loop) | Linear |
| Live dot pulse | 2s | Looping ease-in-out |

---

## 20.3 Page Transitions

When navigating between pages, the content area performs a quick fade-in (opacity 0→1 over 200ms) as the new page renders. Avoid slide transitions between pages as they can feel disorienting in a content-rich environment.

On mobile, article open transitions: the article content fades in with a very slight upward translate (8–12px, 250ms). This simulates a "lifting" effect without being theatrical.

---

## 20.4 Scroll Animations

Elements entering the viewport (article cards below the fold, section headings) fade in with a subtle upward translate of 16px over 300ms. This is triggered once — elements do not animate every time they enter the viewport.

The Breaking News ticker scrolls continuously at a speed calibrated to be readable (~150 pixels per second). It loops seamlessly.

The Reading Progress bar animates in real-time as the user scrolls — no easing or delay. It must feel perfectly in sync with scroll position.

---

## 20.5 Hover Animations (Desktop)

- **Article card image:** Scale from 1.0 to 1.03 over 300ms. Overflow hidden on the card so the image scales within its container.
- **Article card elevation:** Shadow increases from Level 0 to Level 2 over 200ms.
- **Navigation links:** Underline animates from left to right over 200ms.
- **Buttons:** Background color shift over 150ms.
- **Category badges:** Subtle background fill appears over 150ms.
- **Accordion chevron:** Rotates 180° over 200ms when open/close toggled.

---

## 20.6 Loading Animations

**Skeleton screens:** All card grids, article feeds, and list views show skeleton placeholders while loading. Skeleton elements match the exact layout of real content. A smooth shimmer (a lighter highlight that moves left-to-right) indicates active loading.

**Image loading:** Use a low-quality blurred placeholder (LQIP) that transitions to full resolution as the image loads. No jarring "pop" of content.

**Button loading state:** When a form is submitting, the button shows a small inline spinner and its label changes to "Submitting…". The button is disabled during this state.

---

## 20.7 Micro-interactions

- **Search icon tap (mobile):** The overlay slides down from the top with a 250ms ease-out.
- **Share button tap:** Action sheet slides up from bottom (mobile) in 250ms.
- **Audio play/pause:** The play icon transitions to a pause icon with a quick cross-fade, not an abrupt switch.
- **Newsletter subscribe success:** The input field and button transition to a success message — the form elements fade out as the success text fades in.
- **Accordion open:** Height animates from 0 to auto (use max-height technique for CSS, or JS-measured for precision). Content fades in simultaneously.
- **Toast appearance:** Slides in from bottom-right (desktop) or bottom-center (mobile). Slides back out on dismiss.

---

## 20.8 Modal & Drawer Animations

**Modal:** Background overlay fades to 50% opacity (200ms). Modal panel scales from 97% to 100% and fades in (250ms). Combined effect is subtle and elegant.

**Mobile Drawer (menu):** Slides in from the right edge of the screen over 300ms. Backdrop darkens simultaneously. Swipe-right to close also at 300ms.

**Bottom Sheet (mobile):** Slides up from the bottom over 300ms. Spring physics are not recommended here — use simple ease-out for a premium, controlled feel.

---

## 20.9 Reduced Motion

All animations respect the `prefers-reduced-motion` media query. When enabled:
- Page transitions are instant (no fade)
- Scroll animations are disabled
- Hover effects are instant (no transition duration)
- Skeleton shimmer is static (no movement)
- Ticker scrolls at half speed or is replaced with a static display

# SECTION 21: ACCESSIBILITY BLUEPRINT

## 21.1 Color Contrast

- All body text on white background: minimum 7:1 contrast ratio (WCAG AA requires 4.5:1; the platform targets the higher AA Large / AAA standard)
- Large text (heading, display): minimum 4.5:1
- UI components (button labels, input borders): minimum 3:1
- Category badges: text on badge background must meet 4.5:1
- Error text on white: must meet 4.5:1

All contrast ratios to be verified with a tool (e.g., Colour Contrast Analyser) during the design review stage.

---

## 21.2 Font Sizing

- No text smaller than 12px in the published interface (12px is an absolute minimum for micro-labels)
- Body text: 16px minimum on all breakpoints
- Users can scale text using browser zoom — the layout must not break at 200% zoom
- Do not use CSS that prevents text scaling (`-webkit-text-size-adjust: none`)

---

## 21.3 Keyboard Navigation

- Every interactive element (links, buttons, inputs, modals, dropdowns) must be fully operable via keyboard
- Tab order must match the logical visual flow of the page (top-left to bottom-right)
- Modal dialogs must trap focus inside when open
- Dropdown menus must be navigable with arrow keys; Escape closes them
- Skip navigation link: A "Skip to main content" link is the first focusable element on every page, hidden until focused

---

## 21.4 Focus States

- All focusable elements must have a clearly visible focus indicator — the browser's default outline is acceptable but ideally the platform provides a custom focus style (2px solid ring in the brand accent color, 2px offset from element)
- Focus indicators must never be removed with `outline: none` without a custom replacement
- Focus indicators must meet 3:1 contrast ratio against adjacent colors

---

## 21.5 Screen Reader Support

- All images must have meaningful `alt` text. Decorative images use `alt=""`
- The reading progress bar must be marked `aria-hidden="true"` (decorative)
- The Breaking News ticker region must be an `aria-live="polite"` region or updates must be non-disruptive
- Live status indicators ("LIVE", "BREAKING") must convey meaning via text, not color alone
- Audio player controls must have ARIA labels (`aria-label="Play episode"`, etc.)
- Article cards must be implemented as links (`<a>`) wrapping the entire card, or as individual link elements with meaningful link text
- Navigation landmark roles: `<header>`, `<nav>`, `<main>`, `<aside>`, `<footer>` must all be used correctly
- Forms: All inputs must have associated `<label>` elements (not just placeholder text)

---

## 21.6 Touch Targets

- Minimum touch target: 44×44px on all interactive elements
- Targets should have at least 8px spacing between adjacent interactive elements to prevent mis-taps
- The bottom navigation bar items must each have the full height of the bar as a touch target

---

## 21.7 Semantic HTML Hierarchy

- One `<h1>` per page only (the article headline or page title)
- Heading levels never skip (H1 → H2 → H3, not H1 → H3)
- Article body sub-headings use H2 and H3 inside the article `<article>` element
- Lists are marked up with `<ul>` / `<ol>` + `<li>`, never simulated with line breaks
- Tables include `<thead>`, `<tbody>`, `<th scope="col">` for screen reader navigation

---

## 21.8 Forms Accessibility

- Error messages appear adjacent to the relevant field (not just at the top of the form)
- Error messages are announced via `role="alert"` or `aria-live="assertive"` after submission failure
- Required fields are marked with `aria-required="true"` in addition to visual indicators
- Autocomplete attributes are used on common fields (name, email, tel) for assistive technology compatibility

---

# SECTION 22: PERFORMANCE BLUEPRINT

## 22.1 Loading Philosophy

The user's first impression is formed in the first 2 seconds. If the site feels slow in that window, trust is damaged before any content has been read. Performance is a design deliverable, not a technical afterthought.

## 22.2 Core Web Vitals Targets

| Metric | Target |
|---|---|
| LCP (Largest Contentful Paint) | < 2.0 seconds |
| FID / INP (Interaction Delay) | < 100ms |
| CLS (Cumulative Layout Shift) | < 0.1 |
| TTFB (Time to First Byte) | < 600ms |

---

## 22.3 Image Optimization

- All images served in modern formats: WebP primary, JPEG fallback
- Responsive images using `srcset` and `sizes` — the browser downloads only the resolution needed for the device
- Hero images: preloaded (`<link rel="preload">`) to improve LCP
- All images below the fold: lazy loaded (`loading="lazy"`)
- No images with intrinsic dimensions left unspecified (always set `width` and `height` attributes to prevent CLS)
- Low-quality image placeholders (LQIP) for perceived performance

---

## 22.4 Skeleton Screens

Every list, grid, and feed shows skeleton placeholder elements during the data fetch. Skeletons:
- Match the exact layout of the real content
- Use an animated shimmer effect
- Never show a spinning loader as a replacement for content layout (spinners cause CLS and feel slower)

---

## 22.5 Lazy Loading

- Images below the fold: `loading="lazy"`
- Comments section (if added): loaded only when user scrolls near it
- Advertisement scripts: loaded asynchronously, deferred until after main content
- Third-party embeds (YouTube, etc.): facade pattern — show a thumbnail with a play button; the iframe only loads when the user clicks play

---

## 22.6 Infinite Scrolling vs. Pagination

- **Homepage Latest News feed:** Infinite scroll (or "Load More" button as a hybrid) — users expect continuous scrolling for news feeds
- **Search results:** Paginated with "Load More" — allows users to maintain position when navigating back from a result
- **Category pages:** "Load More" button preferred — gives users control over the loading moment
- All infinite scroll implementations must include a "You've reached the end" state and "Back to Top" affordance

---

## 22.7 Caching Strategy

- Static assets (CSS, JS, fonts, logo): aggressively cached with long TTL (1 year, with content hash in filename for cache-busting on updates)
- Article pages: short-to-medium cache (5–15 minutes) with stale-while-revalidate pattern
- Breaking news ticker and live updates: no caching (always fresh)
- Homepage: short cache (60–120 seconds) with background revalidation

---

## 22.8 Font Loading

- Use `font-display: swap` for all web fonts to prevent invisible text during load
- Preload the heading font and body font `woff2` files in the document `<head>`
- Limit the number of font files: 2 typefaces maximum, each in 2–3 weights. More fonts = more network requests = slower load.
- System font stack as fallback while web fonts load (ensure the system font is dimensionally similar to the target font to prevent CLS from font swap)

---

## 22.9 Third-Party Scripts

- All third-party scripts (analytics, ads) loaded asynchronously
- No third-party scripts in the critical rendering path
- Ad scripts use `async` and `defer` attributes
- YouTube player uses facade (poster + play button) until interaction — prevents the YouTube iframe from blocking page load
